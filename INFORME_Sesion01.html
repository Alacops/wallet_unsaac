1. Objetivos

  • Construir un aplicativo de finanzas personales (Wallet UNSAAC) aplicando arquitectura por capas (domain · data · presentation · core).
  • Gestionar el estado de la interfaz con el patrón BLoC (Cubit), separando la lógica de la vista.
  • Implementar tema Material 3 claro/oscuro con una conexión preparada para Firebase.
  • Resolver los cuatro retos de la guía: tema persistente, saldo privado, estados de carga/éxito/error y color semilla configurable.
  • Verificar el resultado con pruebas automatizadas y análisis estático sin observaciones.

3. Arquitectura del proyecto

El código separa responsabilidades en cuatro bloques. La regla de oro es que las dependencias apuntan hacia adentro: la presentación conoce al dominio, pero el dominio no sabe nada de Flutter ni de los Cubits.

lib/
├── main.dart            # arranque: binding → preferencias → Firebase → runApp
├── app.dart             # providers + MaterialApp (tema conectado al Cubit)
├── core/                # transversal: config, tema, utilidades, perfil
│   ├── config/          # app_profile, firebase_status, firebase_bootstrap
│   ├── theme/           # ThemeCubit, ThemePreferences, AppTheme
│   └── utils/           # formato de soles y fechas
└── features/wallet/
    ├── domain/          # REGLAS: Movement, WalletSummary, WalletRepository
    ├── data/            # InMemoryWalletRepository (contrato implementado)
    └── presentation/    # Cubits, páginas y widgets (lo que se ve)

Arranque: main.dart

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();                 // enlaza Flutter con el SO
  final themePreferences = await ThemePreferences.create();  // lee tema guardado (Reto 1)
  final firebaseStatus   = await FirebaseBootstrap.initialize();
  runApp(WalletApp(firebaseStatus: firebaseStatus,
                   themePreferences: themePreferences));
}

main.dart orquesta el arranque: no contiene lógica de negocio ni de interfaz. Lee primero las preferencias de tema para que el primer frame use el modo correcto (sin parpadeo), prepara Firebase con tolerancia a fallos y entrega el control a WalletApp, que inyecta el repositorio y los tres Cubits.

4. Los cuatro retos

Cada reto se resuelve como un estado nuevo bien modelado. La pantalla solo escucha estados con BlocBuilder; nunca modifica datos a mano.

Reto 1 — Tema persistente entre sesiones

ThemePreferences guarda el modo y el color con shared_preferences; se leen antes de runApp. El botón recorre claro → oscuro → sistema → claro, y un valor corrupto cae en system sin romper el arranque.

theme_preferences.darttheme_cubit.dartmain.dart

Reto 2 — Saldo privado

PrivacyCubit (estado inmutable con Equatable) oculta los importes. Los widgets no deciden: reciben hideBalance/hideAmount y un callback. La decisión vive en el Cubit.

privacy_cubit.dartbalance_card.dartmovement_tile.dart

Reto 3 — Estados de carga / éxito / error

Jerarquía sellada BalanceInitial | BalanceLoading | BalanceSuccess | BalanceFailure. El compilador obliga a cubrir los cuatro casos. Ante un error se muestra el mensaje y el botón Reintentar; RefreshIndicator permite recargar.

balance_cubit.dartbalance_state.dartwallet_home_page.dart

Reto 4 — Color semilla configurable

seedColor vive en ThemeState; AppTheme recalcula toda la paleta Material 3 con ColorScheme.fromSeed. El cambio se aplica en caliente a toda la app mediante BlocBuilder<ThemeCubit>.

theme_state.dartapp_theme.dartseed_color_selector.dart

Diagrama evento → estado (Reto 3):
[ app arranca ]  BalanceCubit..load()
      ▼
emit(BalanceLoading())  ───────────────►  BlocBuilder → spinner
      │  await repository.loadSummary()
      ▼
  ┌─ éxito ─► emit(BalanceSuccess(summary)) ─► saldo + lista
  └─ error ─► emit(BalanceFailure(mensaje)) ─► error + "Reintentar"

7. Conclusiones

  • La separación por capas deja las reglas de negocio aisladas de Flutter, lo que facilita las pruebas y el cambio de origen de datos (hoy en memoria, mañana Firebase).
  • El patrón BLoC impone una frontera limpia: los widgets solo escuchan estados, de modo que cada reto se modela como un estado nuevo y no como código disperso.
  • Las clases selladas del estado del saldo obligan a cubrir todos los casos (carga, éxito, error), evitando olvidos en la interfaz.
  • Los cuatro retos quedan integrados y verificados con 22 pruebas y análisis estático sin observaciones.
