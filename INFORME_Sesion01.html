2. Resumen del trabajo

Se construyó Wallet UNSAAC, una aplicación Flutter de finanzas personales organizada en arquitectura por capas (domain · data · presentation · core) y con gestión de estado mediante el patrón BLoC (Cubit). Sobre esa base se resolvieron los cuatro retos de la sesión. El Reto 1 hace persistente el tema entre sesiones guardándolo con shared_preferences y leyéndolo antes de runApp; un valor corrupto cae en system sin romper el arranque. El Reto 2 añade un PrivacyCubit que oculta los importes como estado de presentación, sin tocar los datos. El Reto 3 modela el saldo con una jerarquía sellada (BalanceInitial/Loading/Success/Failure) que obliga a cubrir carga, éxito y error, con mensaje y botón de reintento. El Reto 4 parametriza el color semilla y recalcula toda la paleta Material 3 con ColorScheme.fromSeed. Todo se verificó con 22 pruebas automatizadas en verde y flutter analyze sin observaciones. La decisión técnica que más destaca es modelar cada reto como un estado tipado, de modo que la interfaz solo escucha estados y nunca manipula datos a mano.

Palabras clave: Flutter; patrón BLoC; arquitectura por capas; gestión de estado; pruebas automatizadas.

4. Reto 1 — Tema persistente entre sesiones

4.1. Objetivo y alcance

Lograr que el modo de tema elegido (claro / oscuro / sistema) sobreviva al cierre completo de la app. Queda fuera del alcance la sincronización del tema en la nube entre dispositivos.

4.2. Diseño de la solución

El modo se guarda en disco con shared_preferences y se lee antes de runApp, de modo que el primer frame ya usa el modo correcto (sin parpadeo). El ThemeCubit escribe cada cambio después de emit. Un valor desconocido o nulo se resuelve a ThemeMode.system.

ElementoDecisiónJustificación
Almacenamientoshared_preferencesPersistencia local simple, suficiente para una preferencia de UI
Lectura inicialEn main, antes de runAppEvita el parpadeo del primer frame con el modo equivocado
Ciclo de temasclaro → oscuro → sistema → claroUn solo botón recorre los tres modos de forma predecible

4.3. Implementación

theme_cubit.dartGobierna el temaCiclo de modos y guardado tras emit

ThemeMode loadMode() => themeModeFromName(_prefs.getString(_modeKey));

ThemeMode themeModeFromName(String? name) => ThemeMode.values.firstWhere(
      (mode) => mode.name == name,
      orElse: () => ThemeMode.system,   // valor corrupto o nulo → system
    );

// ThemeCubit: recorre los modos y persiste cada cambio
Future<void> toggle() {
  final next = switch (state.mode) {
    ThemeMode.light  => ThemeMode.dark,
    ThemeMode.dark   => ThemeMode.system,
    ThemeMode.system => ThemeMode.light,
  };
  return setMode(next);
}

Future<void> setMode(ThemeMode mode) async {
  emit(state.copyWith(mode: mode));
  await _preferences.saveMode(mode);   // se guarda después de emitir
}

La lectura vive en main.dart (capa de arranque) y la persistencia en theme_preferences.dart (core), separada del Cubit para poder probarla aislada.

5. Reto 2 — Saldo privado

5.1. Objetivo y alcance

Permitir ocultar y mostrar todos los importes (saldo, totales y movimientos) con un toque, sin recargar la pantalla ni alterar los datos. Queda fuera persistir la preferencia de privacidad entre sesiones.

5.2. Diseño de la solución

La privacidad es un estado de presentación: no cambia los datos, solo cómo se dibujan. Un PrivacyCubit guarda un booleano hidden y los widgets reciben ese dato con un callback; ellos no deciden nada.

ElementoDecisiónJustificación
EstadoPrivacyState(hidden) con EquatableEstado inmutable y comparable para reconstrucciones mínimas
Widgets afectadosSaldo, totales y movimientosLa máscara es transversal a toda la lista
PersistenciaNoLa privacidad es temporal, propia de la sesión actual

5.3. Implementación

ArchivoPropósitoCambios realizados

balance_card.dartMuestra el saldoEnmascara según hideBalance
movement_tile.dartFila de movimientoEnmascara el importe
class PrivacyCubit extends Cubit<PrivacyState> {
  PrivacyCubit() : super(const PrivacyState());

  void toggle() => emit(state.copyWith(hidden: !state.hidden));
}

El Cubit es mínimo a propósito: toda la decisión de «ocultar o mostrar» vive en un único lugar y los widgets solo reaccionan al estado.

6. Reto 3 — Saldo con estados de carga, éxito y error

6.1. Objetivo y alcance

Reemplazar un FutureBuilder por estados explícitos de carga, éxito y error, con mensaje y botón de reintento. Queda fuera el reintento automático con backoff.

6.2. Diseño de la solución

El saldo se modela con una jerarquía sellada; el compilador obliga a cubrir los cuatro casos en el switch de la vista. La pantalla no habla con el repositorio: solo con el BalanceCubit. El error se representa como un estado con mensaje y el reintento vuelve a llamar load().

Future<void> load() async {
  emit(const BalanceLoading());
  try {
    final summary = await _repository.loadSummary();
    if (isClosed) return;                 // evita emit tras cerrar el Cubit
    emit(BalanceSuccess(summary));
  } on Exception {
    if (isClosed) return;
    emit(const BalanceFailure(
      'No se pudo cargar el resumen de la billetera.'));
  }
}

// Vista: el switch sellado obliga a cubrir los cuatro casos
switch (state) {
  BalanceInitial() || BalanceLoading() => const CircularProgressIndicator(),
  BalanceFailure(:final message)        => _ErrorView(message: message,
      onRetry: () => context.read<BalanceCubit>().load()),
  BalanceSuccess(:final summary)        => _SummaryView(summary: summary),
};

El guard isClosed impide emitir sobre un Cubit ya cerrado (por ejemplo, si el usuario abandona la pantalla mientras la carga está en curso).

7. Reto 4 — Color semilla configurable

7.1. Objetivo y alcance

Permitir elegir entre varios colores semilla y que la selección se aplique a toda la app, en claro y oscuro, en caliente. Queda fuera ofrecer un selector de color libre (rueda RGB).

7.2. Diseño de la solución

El color semilla es un campo del ThemeState; AppTheme lo recibe como parámetro y deriva toda la paleta con ColorScheme.fromSeed. El selector usa BlocSelector para reconstruir solo el indicador del punto activo y no toda la hoja.

ElementoDecisiónJustificación
Campo de estadoseedColor en ThemeStateUn único origen para el color activo
TemaColorScheme.fromSeedDeriva toda la paleta sin fijar colores a mano
SelectorBlocSelector por puntoReconstruye solo el indicador, no toda la pantalla
PersistenciaSí (shared_preferences)El color también sobrevive al cierre

7.3. Implementación

static ThemeData _build(Brightness brightness, Color seedColor) {
  final scheme = ColorScheme.fromSeed(
    seedColor: seedColor,
    brightness: brightness,          // misma semilla, claro y oscuro
  );
  return ThemeData(useMaterial3: true, colorScheme: scheme, ...);
}

// Cada punto se reconstruye solo si cambia el color activo

8. Conclusiones y aprendizajes

  1. Leer el tema en main antes de runApp eliminó el parpadeo del primer frame: el modo guardado se verifica en la Figura 2 y en la prueba de persistencia.
  2. Modelar el saldo con una jerarquía sellada obligó, por compilación, a cubrir carga, éxito y error; esto se verifica con las pruebas de balance_test.dart (Loading→Success y Loading→Failure) y la Figura 6.
  3. Parametrizar el color con ColorScheme.fromSeed y aislar la reconstrucción con BlocSelector permitió cambiar la paleta en caliente sin repintar toda la hoja, verificado por seed_color_test.dart y las Figuras 7 y 8.
